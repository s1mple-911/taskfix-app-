4) KONTRAKT (mijoz shunga tayanadi)
------------------------------------------------------------
  POST https://nnpsbwsppgxbytlfloth.supabase.co/functions/v1/aros-staff-proxy

  1. { action:'list', workspace_id, search?, page?, page_size? }
       → { ok:true, count, page, page_size, has_next, results:[…] }
       ⚠️ page_size manbada 100 ga cheklangan (jami ~135 hodim) — EF ham
          100 dan katta so'rovni 100 ga tushiradi.

  2. { action:'detail', workspace_id, source_id }
       → { ok:true, employee:{…} }   (bu yerda `branches[]` — ko'plik)

  3. { action:'schedule', workspace_id, source_id, date_from?, date_to? }
       → { ok:true, schedule:{ employee_id, date_from, date_to, days:[…] } }

  4. { action:'schedule_bulk', workspace_id, source_ids:[…≤25], date_from?, date_to? }
       → { ok:true, schedules:{ "<id>":{…} }, failed:[{source_id, error}] }
       Serverda parallel (6 tadan) — 130 round-trip o'rniga 6 chaqiruv.
       ⚠️ `schedules` KALITI = mijoz YUBORGAN xom id (EF uni normallashtirib
          qaytarmaydi) — javobni yuborilgan qiymat bo'yicha qidiring.
          Xato qatorida ham xom qiymat, 64 belgigacha kesilgan holda.
       ⚠️ UMUMIY MUDDAT 60s: bo'laklar ketma-ket ketgani uchun eng yomon holatda
          5 × 20s ≈ 105s bo'lardi va EF limitiga urilib BUTUN javob yo'qolardi.
          Endi ulgurmagan id'lar so'ralmaydi — ular `failed` ga
          'upstream_timeout' bilan tushadi, olingan jadvallar SAQLANADI.
          Ya'ni `schedules` to'liq bo'lmasligi mumkin — mijoz `failed` ni
          O'QIShI va o'sha id'lar uchun qayta urinishi kerak.

  Xato: { ok:false, error:'<kod>', message:"<o'zbekcha matn>", detail, v }

5) TEKSHIRISH (curl)
------------------------------------------------------------
  Kerak:
    <ANON_KEY>  — Project Settings → API → anon public
    <USER_JWT>  — owner/admin sifatida kirgan sessiya tokeni.
                  TaskFix ochiq turganda brauzer konsolida:
                    (await sb.auth.getSession()).data.session.access_token

  5.1 Ro'yxat (1-sahifa):
    curl -s -X POST \
      "https://nnpsbwsppgxbytlfloth.supabase.co/functions/v1/aros-staff-proxy" \
      -H "apikey: <ANON_KEY>" \
      -H "Authorization: Bearer <USER_JWT>" \
      -H "Content-Type: application/json" \
      -d '{"action":"list","workspace_id":"12b22aa6-dc45-4197-ae84-2e32e3cd56c2","page":1,"page_size":100}'
    Kutilgan: {"ok":true,"count":135,...,"results":[...]}

  5.2 Qidiruv:
      -d '{"action":"list","workspace_id":"12b22aa6-...","search":"Akobir"}'

  5.3 Bitta hodim (branches[] bilan):
      -d '{"action":"detail","workspace_id":"12b22aa6-...","source_id":42}'

  5.4 Jadval:
      -d '{"action":"schedule","workspace_id":"12b22aa6-...","source_id":42,
           "date_from":"2026-08-01","date_to":"2026-08-31"}'

  5.5 Ommaviy jadval:
      -d '{"action":"schedule_bulk","workspace_id":"12b22aa6-...",
           "source_ids":[42,43,44],"date_from":"2026-08-01","date_to":"2026-08-31"}'

  5.6 QOROVUL SINOVLARI (bularning HAMMASI rad bo'lishi SHART):
      • boshqa workspace_id  → 403 forbidden_workspace
      • oddiy a'zo JWT'si    → 403 forbidden
      • JWT'siz              → 401 (Verify JWT darvozasi)
      • {"action":"proxy","url":"http://..."} → 400 bad_action
      • "source_id":"1; DROP" yoki "../"      → 400 bad_body
      • "date_from":"2026-13-45"              → 400 bad_body
      • {"action":["list"],...}                → 400 bad_action (massiv — satr emas)
      • source_ids da 26 ta id                 → 400 too_many_ids

 schedule_bulk ichidagi `failed[].error`: yuqoridagi kodlar + `bad_id`
 (id butun son emas). Bitta id yiqilsa qolganlari baribir qaytadi.
 `upstream_timeout` bu yerda ikki ma'noli bo'lishi mumkin: (a) o'sha id
 uchun manba 20s da javob bermadi, (b) 60s umumiy muddat tugagani uchun
 u UMUMAN so'ralmadi. Ikkalasida ham qayta urinish to'g'ri yo'l.

 ⚠️ upstream_auth chiqsa BIRINCHI tekshiriladigan narsa — sxema:
    `Api-Key <token>` (Token / Bearer / Basic — 401 beradi). Kodda to'g'ri
    yozilgan; demak muammo kalitning o'zida.
